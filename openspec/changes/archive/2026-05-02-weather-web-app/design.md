## Context

目标产品是一个完整的智能天气预报 Web 应用。用户核心路径是：搜索城市、查看实时天气和预报、收藏常用城市、订阅天气推送，并向 AI 助手询问天气相关问题。

系统需要同时处理三类外部能力：

- 天气数据：用于城市天气、湿度、风速、天气状态和预报。
- 城市解析：用于把用户输入的城市名称解析为明确地点。
- AI 问答：用于回答天气相关问题和提供上下文建议。

项目采用前后端分离架构：

- 前端：Vue 3 + Vite + TypeScript，用于构建城市搜索、天气展示、收藏城市、AI 助手和通知设置界面。
- 后端：Spring Boot + Spring WebFlux，运行时使用 Reactor Netty，用于提供 REST API、WebSocket 或流式接口、天气数据代理、AI 助手代理和推送相关服务。
- 数据库：PostgreSQL，用于保存用户、收藏城市、天气查询历史、通知订阅、AI 问答记录和必要的天气缓存。

## Goals / Non-Goals

**Goals:**

- 提供可用的城市天气查询体验。
- 展示温度、湿度、风速、天气状态、更新时间等核心天气信息。
- 提供天气相关 AI 助手，回答用户问题并结合当前城市天气上下文。
- 支持收藏城市，并为收藏城市提供天气摘要。
- 支持天气推送订阅、权限处理和通知频率控制。
- 提供移动端和桌面端都可用的 Web 体验。

**Non-Goals:**

- 不自行构建气象预测模型，天气数据优先来自可靠第三方或官方数据源。
- 不把 AI 助手作为官方灾害预警来源。
- 不在缺少实时数据时编造天气、告警或城市覆盖信息。
- 不在首版实现复杂社交、地图编辑或专业气象分析工作台。

## Decisions

### Application structure

采用前后端分离的单页 Web 应用结构，主界面包含：

- 城市搜索区：输入城市名称，展示候选地点，触发天气查询。
- 天气详情区：展示当前天气、核心指标、多日预报和数据更新时间。
- 收藏城市区：展示收藏城市及天气摘要，支持快速切换。
- AI 助手区：以聊天方式回答天气相关问题。
- 通知设置区：对收藏城市开启或关闭推送。

### Backend and database architecture

后端使用 Spring Boot 组织业务模块，使用 WebFlux/Reactor Netty 提供基于 Netty 的异步网络能力。普通业务接口通过 REST API 暴露；需要实时更新或流式输出的能力可以使用 WebSocket、Server-Sent Events 或响应式流式接口实现。

PostgreSQL 是系统的主数据库，至少需要支持以下数据：

- 用户信息：用于区分不同用户的数据归属。
- 收藏城市：保存城市标识、展示名称、经纬度或天气数据源地点编码。
- 天气查询历史：记录用户查询过的城市和查询时间。
- 通知订阅：记录用户对收藏城市的推送配置、权限状态和通知频率。
- AI 问答记录：保存用户问题、助手回答、关联城市和创建时间。
- 天气缓存：缓存近期天气数据，降低外部天气接口调用频率，并支持失败时展示旧数据。

### User identity and ownership

收藏城市、通知订阅和 AI 问答记录都必须有明确数据归属。首版可以支持正式登录用户，也可以支持匿名会话用户，但两种模式都需要稳定的用户标识：

- 登录用户：使用后端用户 ID 作为收藏、通知订阅和 AI 记录的 owner。
- 匿名用户：后端分配匿名会话 ID，并把数据隔离在该匿名身份下；匿名数据不应与其他用户共享。
- 无法确定身份：禁止写入收藏、通知订阅和 AI 历史，避免产生无 owner 数据。

跨设备恢复只对可重新识别的用户成立。匿名会话可以支持刷新恢复，但不默认保证跨设备恢复。

### Weather data flow

1. 用户输入城市。
2. 系统调用城市解析服务，得到明确地点。
3. 系统调用天气数据服务，获取当前天气和预报。
4. 前端展示天气数据，并把当前城市上下文提供给 AI 助手。
5. 若用户收藏城市，后端将城市标识、展示名称和用户关系保存到 PostgreSQL。

### AI assistant behavior

AI 助手必须区分“已有天气上下文”和“缺少实时数据”两种状态：

- 有当前城市天气时，可以基于天气信息回答穿衣、出行、运动、通勤、雨具等问题。
- 没有当前城市天气时，应提示用户先查询城市，或只回答通用天气知识。
- 涉及极端天气和安全决策时，应建议用户关注官方气象或应急渠道。

### Favorites and notifications

收藏城市必须通过后端保存到 PostgreSQL，以满足刷新页面、重新登录或跨设备访问时的数据恢复需求。前端可以使用本地状态提升交互速度，但数据库是最终持久化来源。

天气推送应采用显式授权模型：

- 未授权前不发送通知。
- 用户可以按城市开启或关闭通知。
- 推送内容包括城市、天气变化、严重程度、时间和简短建议。
- 对重复或短时间内频繁变化的天气事件进行合并或限流。

推送通道拆分为两类：

- 浏览器 Web Push：用于用户未打开应用时的后台通知，需要 HTTPS、Service Worker、浏览器通知权限和持久化 push endpoint。
- 应用内实时更新：用于用户正在使用应用时更新通知状态、天气变化或 AI 流式输出，可以使用 SSE、WebSocket 或 WebFlux 响应式流实现。

Web Push 是后台通知的交付机制；SSE/WebSocket 不替代后台推送，只负责应用打开期间的实时体验。

### Error and fallback strategy

- 城市无法解析：展示“未找到城市”或候选城市列表。
- 天气接口失败：展示重试入口，并保留可用的旧数据。
- AI 服务失败：展示失败状态并允许重试。
- 通知权限被拒绝：保持关闭状态，提示用户可在浏览器设置中开启。

## Risks / Trade-offs

- “任意城市”依赖城市解析和天气数据源覆盖范围，系统必须明确处理未覆盖城市。
- 浏览器推送能力受权限、浏览器、HTTPS 和后台服务限制，需要在任务阶段验证目标环境。
- 匿名会话可以降低首版登录成本，但跨设备恢复和长期数据保留能力弱于正式登录用户。
- AI 助手可能被用户用于高风险决策，必须设置回答边界，不替代官方预警。
- PostgreSQL 提升了系统完整性和可展示性，但也要求设计表结构、连接配置、迁移脚本和基础数据访问层。
- Spring WebFlux/Reactor Netty 适合实时通知和流式交互，但实现复杂度高于传统阻塞式 MVC，需要控制首版范围。

## Context

当前应用是 Vue 3 + Vite + TypeScript 前端和 Spring Boot WebFlux 后端组成的智能天气 Web 应用。用户搜索城市后，页面已展示天气、收藏、通知和 AI 天气助手；本变更在同一搜索上下文中增加当地美食和游玩地点推荐，使搜索地区成为天气与出行建议的统一入口。

推荐内容需要外部 AI 能力生成或整理，同时要包含可展示图片和信息来源链接。由于 AI 输出可能不稳定，后端需要把 AI 响应约束为结构化数据，并在返回前校验排名、数量、来源 URL 和图片 URL。推荐数据需要持久化到 PostgreSQL，形成按地区和类别复用的推荐池，既减少重复 AI 调用，也支持多用户共享已生成的高质量推荐。

## Goals / Non-Goals

**Goals:**

- 根据用户当前搜索地区展示两组推荐：5 个美食、5 个游玩地点。
- 每个推荐项包含排名、名称、图片插图、介绍、来源标题和来源超链接。
- 推荐区域右上角提供“换一批”白底按钮，文字右侧带刷新图标，用户点击后获取当前地区新的、不重复的一批推荐。
- 将推荐内容和批次持久化到数据库，用于当前用户去重和多用户复用。
- 后端提供稳定的推荐 API，并把 AI 输出规范化为前端可直接渲染的数据结构。
- 前端在地区变化时刷新推荐卡片，并提供加载、失败、空状态和重试能力。
- 实现后通过 Chrome 辅助功能展示推荐区域的语义、键盘访问、图片替代文本和链接可识别性，让用户过一遍并确认样式。

**Non-Goals:**

- 不实现预订、导航、票务购买或餐厅下单能力。
- 不把 AI 推荐作为官方旅游、食品安全或营业状态证明。
- 不要求用户手动编辑或收藏单个推荐项。

## Decisions

### Recommendation API shape

后端新增按地区查询推荐的接口，例如 `GET /api/recommendations/local?locationId=...&displayName=...`。接口返回同一个地区下的两个列表：

- `foods`: 5 个美食推荐。
- `places`: 5 个游玩地点推荐。

每个条目包含 `rank`、`name`、`description`、`imageUrl`、`imageAlt`、`sourceTitle`、`sourceUrl` 和可选的 `sourceName`。前端不解析 AI 原始文本，只消费结构化 JSON。

后端再提供换一批能力，例如 `POST /api/recommendations/local/refresh`，入参包含当前地区、当前已展示的推荐项 ID 或批次 ID。接口返回新的 `foods` 和 `places` 批次，并保证在可用推荐池范围内不重复返回当前批次条目。

替代方案是让前端直接调用 AI 服务并解析文本。该方案会暴露密钥、增加提示词耦合，并使错误处理分散在 UI 层，因此不采用。

### AI generation and validation

后端负责调用 AI 推荐服务，要求 AI 按固定 JSON schema 返回当地代表性美食和旅游地点，并包含来源 URL。后端在返回前执行校验：

- 每个类别必须最多返回 5 项；不足 5 项时返回实际可验证项目并带状态说明。
- 排名必须从 1 开始连续排序。
- 来源 URL 必须是 HTTP(S) 链接。
- 图片 URL 缺失时使用受控占位图，并让 `imageAlt` 明确描述推荐项。
- 介绍必须是简短摘要，避免冗长文本撑破卡片。

替代方案是把 AI 返回内容原样透传。该方案会让 UI 暴露无效链接、错位排名或不可控文本长度，因此不采用。

### Persistence and reuse

推荐数据持久化到 PostgreSQL，建议至少包含：

- `local_recommendation_items`：地区标识、地区展示名、类别、规范化名称、介绍、图片 URL、图片 alt、来源标题、来源 URL、内容指纹、创建时间、更新时间。
- `local_recommendation_batches`：地区标识、批次类型、批次序号或批次 ID、推荐项 ID 列表、创建时间。
- 可选的 `local_recommendation_views`：用户或匿名会话、地区、类别、已展示推荐项 ID、展示时间，用于给单个用户做更严格的去重。

同一地区推荐池对所有用户共享；用户点击“换一批”时，后端先从数据库推荐池中选择未展示条目，不足时再调用 AI 扩充推荐池并写入数据库。内容指纹用于避免不同 AI 调用产生同名或高度重复推荐项。

替代方案是只按用户保存推荐结果。该方案会导致重复 AI 调用多、跨用户无法复用，也更难积累稳定推荐池，因此不采用。

### Frontend integration

前端在天气搜索成功并确定 `WeatherResult.location` 后触发推荐请求。推荐区域放在天气主内容之后或相邻区域，按页面已有卡片风格实现两个 section：美食推荐和游玩推荐。

每个 section 使用有序列表表达 1-5 排名，卡片内显示图片、排名、标题、介绍和来源链接。移动端以单列滚动展示，桌面端可使用紧凑网格，避免嵌套卡片和横向滚动。

推荐区域右上角放置“换一批”按钮，采用白底、边框样式，文字右侧使用刷新图标。按钮点击后只刷新推荐区域，不重跑天气查询；刷新过程中按钮进入加载/禁用状态，并保留当前内容直到新批次返回或失败。

正式实现推荐卡片 UI 前，需要先做一版可运行的样式预览，使用模拟推荐数据展示美食和游玩地点卡片、“换一批”按钮、桌面布局和移动布局。该预览通过 Chrome 辅助功能展示给用户确认；只有用户确认样式可接受后，才继续把该样式固化到正式数据流、状态处理和 Playwright 样式相关测试中。

### State and fallback behavior

推荐请求有独立加载和错误状态，不阻塞天气展示。地区切换时取消或忽略旧请求结果，避免旧城市推荐覆盖新城市页面。AI 服务失败时展示推荐区域失败状态和重试入口；若某个类别无结果，展示该类别的空状态。

“换一批”失败时保留当前批次并显示轻量错误提示。若数据库推荐池和 AI 扩充后都无法提供新的不重复内容，则按钮应提示暂无更多推荐，而不是重复返回当前批次。

### Accessibility and style confirmation

推荐区域使用语义化标题、`ol`/`li` 排名结构、可识别链接文本和图片 `alt`。实现阶段需要启动前端页面，并用 Chrome 辅助功能能力展示推荐区域，供用户确认：

- 标题层级可理解。
- 来源链接可通过键盘聚焦并读出目的。
- “换一批”按钮可通过键盘聚焦，刷新图标不干扰按钮的可访问名称。
- 图片有非空替代文本或明确装饰属性。
- 桌面和移动视口没有文本重叠、溢出或横向滚动。

## Risks / Trade-offs

- AI 推荐可能包含不准确或过时信息 -> 后端要求来源 URL，前端明确展示来源并避免声称实时营业、价格或开放状态。
- 图片 URL 可能不可用或跨域失败 -> 使用受控占位图和图片错误回退，保持卡片布局稳定。
- 推荐接口可能较慢 -> 推荐加载独立于天气查询，并优先复用数据库推荐池。
- 任意地区可能缺少足够推荐 -> 允许返回不足 5 项并展示说明，但可验证地区应尽量返回完整 5 项。
- 外部 AI 或图片服务成本增加 -> 使用后端缓存、请求去重和超时控制。
- 推荐池长期积累可能出现过期内容 -> 保存更新时间和来源，后续可加入过期刷新策略；首版避免展示实时营业、价格或开放状态断言。
